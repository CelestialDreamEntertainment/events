# Events
Scheduling for events I host with friends, part of the apps suite. Invited friends sign in to see events and RSVP.

> **Status:** v1 runs locally (public and private events, invites, RSVPs, surprise parties). Nothing is deployed yet. Events is the first app, so the first version of the platform is built around what it needs. The shared design lives in the suite README (`../README.md`).

## Access
- **Scopes:** `events:guest` (the base scope, required by every non-public route) and `events:host`. Hosts also hold `events:guest`.
- **Examples:** creating an event requires `events:host`. Handlers can use `user.has('events:host')` for finer-grained behavior, like hosts seeing every RSVP while guests see only their own.
- **Invites:** friends are invited with the `platform-infra` invite script, e.g. `pnpm invite friend@example.com --group events:guest --env prod`, and later through the Admin app.

## Structure
- **Frontend:** `web/`, React + Vite + Mantine + wouter, with the platform `web` package's auth client and typed API client. Date and time fields are plain `datetime-local` inputs plus a time zone picker.
- **Backend:** `api/app.ts` is the routes manifest (`defineApp`), with one handler file per route in `api/handlers/`. `api/routes.gen.ts` is generated by `pnpm types` and gives the frontend its typed client. Likely scheduled jobs, such as reminders, go in the manifest's `schedules` section.
- **IaC (planned):** Terraform using the pinned `platform` modules (`app-api`, `static-site`, `app-auth`).
- **Data:** the `events` database on the environment's Atlas cluster. Nothing else reads it.
- **Email:** any notifications go through SES and are flagged for cost before they're added.

## How events work
- **Visibility:** a public event shows on the calendar for every `events:guest`. A private event shows only to its host and to the emails on its invite list, matched against the signed-in user's email. Anyone else gets a 404 for it, so private events don't leak by id.
- **Hosting:** users with `events:host` create events. Only an event's own host edits or cancels it and sees its invite list. Cancelling keeps the event, marked cancelled, and stops new RSVPs.
- **RSVPs:** going, maybe or not going, with an optional note. Guests see the counts and their own RSVP. Users with `events:host` also see everyone's RSVPs on events they can see.
- **Uninvited guests:** if a guest loses access (removed from the invite list, or a public event goes private), their RSVP stops counting and drops off the host's list. It stays stored, so it comes back if they're invited again.
- **Surprise parties:** a host can make any event a surprise for one or more people (by sign-in email), with a cover story: its own title, times, location and details. Those people see only the cover story, even on a private event they aren't invited to, and their counts only include each other's RSVPs. Everyone else sees the real event, plus who it's for (by name) and the cover story, so nobody spoils it. Only the host sees the emails. A host can't make a surprise for themselves.
- **Times:** stored as instants plus the event's IANA time zone, and shown in that zone.
- **Data:** two collections, `events` and `rsvps` (one RSVP per event and user, id `${eventId}:${userId}`).

## Development
Until the `@sbwp` packages are published to npm, events installs them from a `platform` checkout next to this repo (`file:../platform/packages/*`), so build that first:

```sh
(cd ../platform && pnpm install && pnpm build)
pnpm install
```

- `pnpm dev`: starts local Mongo (Docker), the local API on 4102 and Vite on 5102, with fake sign-in. Tick `events:guest` or `events:host` on the sign-in page to switch roles.
- `pnpm test`: API tests against an in-memory MongoDB, and frontend tests in jsdom, with 100% coverage required.
- `pnpm lint`, `pnpm format`, `pnpm typecheck` (also fails if `api/routes.gen.ts` is stale), `pnpm types`, `pnpm build`.

After changing the `platform` packages, rebuild them and run `pnpm install` again, since `file:` dependencies are copied in at install time. CI checks out `platform` at the commit pinned in `.github/workflows/ci.yml`.

## Releases
Merging to main deploys to dev. Prod deploys after manual approval on the GitHub `prod` environment and gets a date tag. PR titles follow Conventional Commits.
